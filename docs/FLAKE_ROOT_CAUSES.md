# Flaky tests: root causes and what was done

No retries, waits or generous timeouts were added to hide a flake. Each entry says what is known and how sure it is.

| Flake | Root cause | Status |
|---|---|---|
| `MpvDamagedFilesTest.aFileThatIsStillBeingWrittenKeepsPlayingAsItGrows` ("load sensitive") | **A product bug, found and reproduced.** `GrowingFilePolicy.shouldReload` limits reloads to one per second; the engine read its `false` as "the file stopped growing" and completed playback. A player that reaches the new end of the file less than a second after a reload (a fast machine) stopped in the middle of a recording; a slow one did not. The policy now answers `COMPLETE`, `RELOAD` or `WAIT`, and `WAIT` keeps following. | Fixed. 4 of 4 runs failed before on a fast Mac, 5 of 5 pass after; `GrowingFilePolicyTest` covers the new answer. |
| Linux smoke: `video_sample.mkv: no video track was decoded` (twice) and macOS Intel `bothAudioTracksAreListedWithTheirTitlesAndLanguages` (first audio track not selected) | Probable, one cause for both: the engine cached libmpv's track list and, if a read missed an entry or saw nothing selected yet (libmpv resolves the automatic selection a moment after the list appears) while the file was still opening, kept that list until the periodic refresh 20 passes later. The engine now reads again on the next pass when the read does not match the count libmpv reports or has no audio/video track selected (`MpvTrackListWatcher`, a few attempts at most). | Fix in place and unit tested; **not reproduced locally**, so only a run of CI without the flake can confirm it. The earlier "wait up to 3 s for the track" in the smoke check was removed again. |
| macOS Intel/arm64 deinterlace test timeout | Probable: the test asked for playback to advance after each of seven mode changes, but the clip is two seconds long and libmpv pauses at its end (`keep-open`); a slow machine spends the clip on the filter changes and then no progress can ever be seen. (A seek back plus play at the end did not restart playback within 15 s in an experiment, so a fixed-length wait cannot recover.) Now each mode opens the clip afresh and waits for the engine to report *playing* past 100 ms: an event, independent of how much clip is left. | Test rewritten; **not reproduced locally** (this Mac is fast). CI will confirm. The failure message now names the mode and the engine state. |
| iOS audio tap rendered silence once on a CI runner (`AudioEffectsTests`) | **Unknown.** 150 renders under heavy CPU load locally gave no silence and no tap errors. The one path that could produce silence without an error (a failed source-audio call left the output frame count unset) now sets it to zero, and abnormal tap events are recorded (`AudioEffectsController.tapEvents`) and printed if a render is ever silent. The retry in the test was removed. | Not understood. If it recurs, the CI log will say what the tap saw. |
| macOS arm64 packaged-app smoke: `fullscreen-exit` and `resize` "video decoded but the window shows no picture" (once, software renderer) | **Unknown.** The check already waits for libmpv to present a frame after the window change; the pixels sampled from the screen were still dark. Possibly the VM's compositor capture lags the presented frame. Not changed. | Open: new, seen once. |
| macOS Intel packaging: could not resolve `gradle-plugin-internal-jdk-version-probe` (once) | Network failure resolving a Gradle plugin artifact, not our code. | Infrastructure; not changed. |
| Android `Media3GaplessTest.withoutPreparationTheFirstItemCompletes` (failed once in a full emulator run) | A race in the test: it read a list filled by a collector on another thread the instant the engine reported `Completed`. It now waits for the collector to have seen the state (an event, no sleep). | Fixed; 3 of 3 reruns and the full suite (46 tests) pass. |
| Gradle `-q` hid per-test failure lines in my local runs (not a flake) | `-q` suppresses Gradle's test-failure lines, so some "clean" local runs of mine were not clean. | Verified again without `-q`; the final gate runs use full output. |
